## 1. 目标与边界

v0.2 的目标是在保持本地优先、低资源占用和单窗口体验的前提下，把当前固定的
Claude Code / Codex 监控升级为由 ccusage 统一快照驱动的动态 Agent 监控，并只增加
三个轻量信息维度：预估成本、缓存输入占比和数据更新时间。

本版本不加入：

- 模型明细 UI、项目或 Session 分析、月度统计、Burn Rate、通知和用量预测；
- 登录、云同步、API Proxy、插件系统、设置中心、路由或侧边栏；
- 前端 ccusage 原始 JSON 解析、前端价格表或通用 Provider 框架；
- 为满足设计规范而人为增加第二个页面或 Dark Stage。

架构边界保持不变：

```text
local agent records
        -> ccusage 20.0.20 unified sidecar
        + pinned Antigravity focused compatibility sidecar
        -> Rust ccusage adapter
        -> project UsageSummary contract
        -> Tauri command / tray event
        -> React presentation
```

## 2. 已验证事实与设计决策

### 2.1 ccusage 统一结构

已在随应用打包的 ccusage 20.0.20 上验证：

```powershell
ccusage daily --json --offline --by-agent --since <YYYYMMDD>
```

输出顶层包含 `daily` 和 `totals`。统一日报使用 `daily[].period` 表示日期，而不是
当前 focused adapter 使用的 `daily[].date`；每日 `agents[]` 中包含 Agent ID、输入、
输出、缓存创建、缓存读取、总 Token、模型明细和预估成本。

统一调用只保证：

- 未缓存采集只创建一个 ccusage 子进程；
- 所有 Agent 来自同一次快照；
- 超时、stderr、退出码和进程树清理由一个监督边界负责；
- 新 Agent 不再需要新增 CLI 命令常量和调用分支。

它不保证底层只读取一次文件，也不保证耗时或 I/O 减半。当前参考机器 5 轮预研结果：

| 调用 | 平均耗时 |
|---|---:|
| unified daily | 约 345 ms |
| focused Claude | 约 58 ms |
| focused Codex | 约 286 ms |

因此性能验收采用“无显著回退 + 单进程 + 无残留”，不采用“耗时减半”。

### 2.2 Agent 展示策略

- 公共契约中的 Agent ID 是开放字符串，不使用 Rust enum 或 TypeScript 字面量 union。
- Rust adapter 输出 `displayName`。已知特殊名称可使用小型显示映射，未知 ID 使用安全的
  通用格式化回退；不得因为未知 Agent 使整个报告失败。
- 今日列表只显示今日 Token 大于零的 Agent，按 Token 降序、显示名升序稳定排列。
- 只在过去七天出现、但今日为零的 Agent 不占今日列表空间；其历史用量仍进入七日总趋势。
- 没有今日用量时显示空状态，不生成固定的零值 Agent 行。

### 2.3 成本与缓存语义

- UI 使用“Est. cost”或“预估成本”，不得表述为实际账单。
- 成本字段必须允许缺失；未知价格时隐藏成本或显示不可用，不得把缺失误写为 `$0.00`。
- v0.2 不展示 `modelBreakdowns`，adapter 仍应忽略未知 JSON 字段。
- “缓存输入占比”定义为：

```text
cacheReadTokens /
(inputTokens + cacheReadTokens + cacheCreationTokens)
```

- 分母为零时该指标为不可用。不得将它命名为“节省比例”，因为该比例没有计算无缓存时的
  反事实成本。

### 2.4 刷新与陈旧数据

- `collectedAt` 表示 Rust 最近一次成功采集完成的 UTC RFC 3339 时间。
- Dashboard 显示相对时间，例如 `Updated 2m ago`，并定期只更新相对文案。
- 窗口聚焦和手动刷新仍可触发采集；托盘的 5 分钟刷新成功后向窗口发送同一份
  `UsageSummary` 事件，避免额外增加前端采集轮询。
- 刷新失败且存在上次成功数据时，保留旧数据并显示非阻塞的 stale/update-failed 状态；
  只有从未成功加载过数据时才显示全屏错误状态。
- 并发采集保持 single-flight；应用退出后不得再启动新 sidecar。

### 2.5 视觉语言

当前 Dashboard 是读数和趋势阅读界面，定义为 **Light Reading Surface**。Dual-Surface
规范在本项目中只迁移以下规则：

- 暖纸色阅读底、墨色文字梯度、1px hairline 和开放式层级；
- Serif 用于标题，Sans 用于控件和元数据，Mono 用于 kicker 与 tabular 数值；
- Terracotta 用于今日核心值、预估成本和关键操作；
- Indigo 用于趋势、当前/刷新状态和 focus ring；Moss Green 只用于成功状态；
- 不增加卡片网格、pill forest、glassmorphism、装饰性渐变或外部网络字体。

系统暗色兼容可以保留，但它是系统主题降级，不命名为 Dark Stage，也不引入路由级舞台。
任何新增刷新动画必须同时提供 `prefers-reduced-motion` CSS 降级；若加入 JS 动画行为，
还必须有对应的 JS 降级。

## 3. 建议公共数据契约

字段命名以下游序列化后的 camelCase 为准；Rust 使用对应 snake_case。

```ts
interface AgentUsage {
  id: string;
  displayName: string;
  tokens: number;
  inputTokens: number;
  outputTokens: number;
  cacheReadTokens: number;
  cacheCreationTokens: number;
  estimatedCostUsd: number | null;
}

interface DailyUsage {
  date: string;
  totalTokens: number;
  estimatedCostUsd: number | null;
  agents: AgentUsage[];
}

interface UsageSummary {
  collectedAt: string;
  today: DailyUsage;
  last7Days: DailyUsage[];
}
```

实现时只加入 UI 和托盘实际消费的字段。如果 Phase 7 证明每日历史不需要完整 Agent
Token 构成，可将 `last7Days` 的 Agent 明细收窄，但 Rust 与 TypeScript 契约必须同时更新。

数字边界：Rust 聚合继续使用 `u64` 和饱和加法；adapter 测试必须覆盖大值。由于 Tauri
最终序列化为 JavaScript `number`，超过 `Number.MAX_SAFE_INTEGER` 的策略必须在实现 Phase 7
前明确：验证七日单日值不会达到该范围，或改为十进制字符串。不得无说明地丢失精度。

### Phase 8 — 成本、缓存和刷新新鲜度

3. 显示相对更新时间和手动刷新；增加轻量刷新状态。
4. 托盘刷新成功后向已打开窗口发送更新事件。
5. 刷新失败保留最后成功数据；新增 stale 状态与可重试入口。

验收：

- 成本有值、为零、缺失三种 fixture 均正确，缺失值不伪装为零；
- 缓存公式、零分母、四舍五入边界均有单元测试；

- 首次失败显示错误页，已有数据后的失败保留数据并标记陈旧；
- 托盘与窗口消费同一成功快照，不因一个刷新事件启动第二个 sidecar；
- reduced-motion 下没有持续旋转或闪烁动画。

4. 缩减固定垂直冗余；为低高度添加明确的 compact media query。
5. 为 focus-visible、200% 文本缩放、系统明暗主题和 reduced-motion 补齐状态。

### 5.1 Rust adapter 单元测试

- 参数严格包含 `daily --json --offline --by-agent --since <YYYYMMDD>`；

- timeout、poll error、应用 shutdown 后杀死整个进程树并 reap；
- 两个并发请求只有一个实际采集；短期缓存同时缓存成功和失败；
- release 包只使用同目录 `ccusage.exe`，不嵌入开发机绝对路径。

- 事件更新不会触发额外 fetch；组件 unmount 后不更新状态。

优先测试纯函数和状态 reducer。只有确有必要时才增加 UI 测试依赖。

## 7. 性能与发布门禁

### 7.1 参考性能

在同一台机器、同一数据窗口上进行至少 10 次 warm run，记录 median 和 p95：

- unified median 目标不超过旧 focused 两次合计 median 的 125%；
- 参考机器 typical-data median 目标不超过 500 ms，p95 目标不超过 1 s；
- 如因新增已探测 Agent 导致超出相对目标，记录 Agent 数量与原因，由人工判断，不能把
  “一个进程”误报为“资源减半”；
- 每次未缓存刷新只出现一个 ccusage PID，并发峰值为 1；
- 5 分钟空闲观察期间除计划刷新外不出现 sidecar，CPU 应回落到接近空闲基线；
- 成功、失败、超时、隐藏、退出和卸载后残留进程均为 0。

### 7.2 v0.2 发布阻断条件

出现以下任一情况不得发布：

- Claude/Codex 数值相对 v0.1 fixture 回退；
- 未知 Agent、缺失成本或零分母导致崩溃、NaN、Infinity 或伪造 `$0.00`；
- React 直接解析 ccusage JSON，或新增前端价格字典；
- 并发 sidecar 超过 1、刷新风暴、timeout/退出后存在残留进程；
- 默认视口裁切内容，紧凑视口通过隐藏 overflow 伪装为无滚动；
- 安装包依赖 Node、pnpm、Bun 或网络；
- 中文用户路径的 GUI/SQLite/sidecar/卸载任一环节未实际验证；
- 自动化或手工矩阵存在未说明的未执行项。

### 7.3 交付记录
