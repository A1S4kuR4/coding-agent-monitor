## 宿主数据库依赖统一（rusqlite → sqlite 0.37）

**背景**：vendored workspace 的 5 个 adapter（antigravity/goose/hermes/kilo/opencode）
依赖 `sqlite 0.37`（→ `sqlite3-src`，`links = "sqlite3"`）；宿主此前用
`rusqlite 0.40 + bundled`（→ `libsqlite3-sys`，同为 `links = "sqlite3"`）。
cargo 规定同一依赖图内只允许一个 `links = "sqlite3"` 的包，接入
`ccusage-adapter-all` 路径依赖后在解析阶段直接失败。

**决策**：把宿主自身很薄的数据库初始化层（`src-tauri/src/db/mod.rs`，仅建文件 +
两个 PRAGMA）从 rusqlite 迁移到与 vendor 完全一致的
`sqlite = { version = "0.37.0", default-features = false, features = ["bundled", "linkage"] }`，
使最终二进制只有 `sqlite3-src` 一套 SQLite native linkage。

**要点**：

- 这是**宿主数据库依赖统一**，目的仅是消除同一二进制内两个
  `links = "sqlite3"` crate 的冲突；不增加业务表、不扩大数据库职责，
  cache 文件名（`usage-cache.sqlite3`）、WAL / foreign_keys 行为、
  非 ASCII 路径测试全部保持不变。
- **vendor 源码保持不变**——5 个 adapter 未被修改、未加排除 feature、
  未使用任何 sqlite3-src 替身/patch，因此不增加上游同步 patch 负担。
- 对应计划文档 Phase 2（SQLite 单一实现）的宿主侧部分提前在 Gate 0 完成；
  Phase 2 其余验收（只读源 DB 安全失败场景等）不受影响，继续按 Phase 2 执行。

**验证证据**：

- `cargo tree -i sqlite3-src`：单一来源 `sqlite3-src 0.7.0 → sqlite3-sys 0.18 → sqlite 0.37`，
  引用方为宿主 + 上述 5 个 vendored adapter，无其他；
- `cargo tree -i libsqlite3-sys`：`did not match any packages`（已不存在）；
- `cargo test --manifest-path src-tauri/Cargo.toml`：37 passed / 0 failed
  （含 `db::tests::initializes_sqlite_in_a_non_ascii_directory`：中文路径建库、
  重开、journal_mode=wal、连接关闭后文件清理）。

## Gate 0 关闭记录（2026-08-30 复核）

本节关闭 Gate 0 的剩余门禁：vendor 可复现重建、只读验证命令、许可证审计、测试隔离。

### 1. vendor 重建流程（可复现性）

`scripts/vendor-ccusage-import.mjs` 重写为"staging 重建 + 逐字节校验 + 原子换入"：

1. 从固定 commit（upstream `bd7f89b…` tree `0acb7f0e…`；fork `c58c1b3…` tree `c489445d…`）shallow-fetch 到临时目录，校验 commit+tree 身份；
2. 导出 pristine v20.0.20 rust 子集到 staging；重新生成 0001 参考 diff（baseCommit..commit，仅审计用，不应用）；
3. 用 GNU `patch -p1` 应用 `patches/0002-cam-downstream-v20.0.20.patch` —— 这是实际可执行的 CAM downstream patch，覆盖 Antigravity 拆分架构移植、离线定价 build.rs 回退、additive models.dev 条目（`gemini-3.1-pro`）和进程内 PoC seam；0001 为无法应用到 v20.0.20 的原始 PR diff，仅作审计参考保留；
4. 抓取并 SHA-256 校验 LiteLLM 快照；复制已提交的 PATCHES.md（脚本不生成它）；生成器重写 UPSTREAM.toml / pricing-manifest.json；生成 `MANIFEST.sha256`（全部 vendor 文件的 committed-blob SHA-256）；
5. 重建结果与仓库已提交 blob **逐字节比对**（205 文件），任何不一致中止且不触碰现有 vendor；比对通过后才原子换入（换入前备份，失败回滚）；
6. 前置守卫：vendor 树有未提交改动时直接拒绝运行。

**验证**：两次端到端重建通过 —— 首次以 `--adopt-generated` 吸收两个生成器自有 manifest 的规范化改写，提交后以严格模式重跑（`--work-dir .tmp-upstream/rebuild-strict`）成功且换入后 `git status` 对 vendor 目录零差异。即 vendor 可从固定 commit 完整重建到与已提交状态字节一致。

注意：重建必须用 GNU `patch` 而非 `git apply`（staging 位于仓库内时 `git apply` 按 repo root 解析路径）。若直接编辑 vendor 源码而不重新生成 0002 patch，重建的字节比对会失败 —— 这是设计行为，提示先重新生成 patch（流程见 PATCHES.md）。
