## 宿主数据库依赖统一（rusqlite → sqlite 0.37）

**背景**：vendored workspace 的 5 个 adapter（antigravity/goose/hermes/kilo/opencode）
依赖 `sqlite 0.37`（→ `sqlite3-src`，`links = "sqlite3"`）；宿主此前用
`rusqlite 0.40 + bundled`（→ `libsqlite3-sys`，同为 `links = "sqlite3"`）。
cargo 规定同一依赖图内只允许一个 `links = "sqlite3"` 的包，接入
`ccusage-adapter-all` 路径依赖后在解析阶段直接失败。

**决策**：把宿主自身很薄的数据库初始化层（`src-tauri/src/db/mod.rs`，仅建文件 +
两个 PRAGMA）从 rusqlite 迁移到与 vendor 完全一致的
`sqlite = { version = "0.37.0", default-features = false, features = ["bundled", "linkage"] }`，
使最终二进制只有 `sqlite3-src` 一套 SQLite native linkage。

**要点**：

- 这是**宿主数据库依赖统一**，目的仅是消除同一二进制内两个
  `links = "sqlite3"` crate 的冲突；不增加业务表、不扩大数据库职责，
  cache 文件名（`usage-cache.sqlite3`）、WAL / foreign_keys 行为、
  非 ASCII 路径测试全部保持不变。
- **vendor 源码保持不变**——5 个 adapter 未被修改、未加排除 feature、
  未使用任何 sqlite3-src 替身/patch，因此不增加上游同步 patch 负担。
- 对应计划文档 Phase 2（SQLite 单一实现）的宿主侧部分提前在 Gate 0 完成；
  Phase 2 其余验收（只读源 DB 安全失败场景等）不受影响，继续按 Phase 2 执行。

**验证证据**：

- `cargo tree -i sqlite3-src`：单一来源 `sqlite3-src 0.7.0 → sqlite3-sys 0.18 → sqlite 0.37`，
  引用方为宿主 + 上述 5 个 vendored adapter，无其他；
- `cargo tree -i libsqlite3-sys`：`did not match any packages`（已不存在）；
- `cargo test --manifest-path src-tauri/Cargo.toml`：37 passed / 0 failed
  （含 `db::tests::initializes_sqlite_in_a_non_ascii_directory`：中文路径建库、
  重开、journal_mode=wal、连接关闭后文件清理）。
