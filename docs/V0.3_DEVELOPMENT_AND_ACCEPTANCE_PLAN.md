## 1. 决策摘要

v0.3 将 ccusage 的 Rust 采集源码和 Antigravity 适配器源码作为可审计的 vendored source
编译进 Coding Agent Monitor 自身，不再下载、构建、打包或运行 `ccusage.exe` 与
`ccusage-antigravity.exe`。为保留 v0.2 的故障隔离能力，采集不直接在 Tauri UI 进程内执行：父进程
使用 `current_exe()` 启动**同一个 Coding Agent Monitor EXE**的隐藏 worker 模式，通过版本化的
stdin/stdout JSON 协议交换数据，并继续执行超时、进程树终止、退出门禁和 single-flight。

最终安装包只允许包含一个产品 EXE。worker 是该 EXE 的内部启动模式，不是第三个 sidecar，也不建立
新的公开 CLI。

迁移必须保持以下外部行为不变：

- v0.2 React UI、窗口、托盘与刷新/stale 行为；
- `src-tauri/src/usage/mod.rs` 与 `src/types/usage.ts` 定义的 `UsageSummary` 公共契约；
- 开放字符串 Agent ID、Rust 产生 `displayName`、动态今日 Agent 列表和未知 ID fallback；
- 纯本地、无登录、无遥测、运行时零网络采集；
- Windows 10/11 x64、非 ASCII 路径和安装/卸载支持；
- 未知价格返回 `null`、不伪造 `$0.00`，以及现有 reasoning/unclassified 语义。

本计划制定前已完整阅读：

- `AGENTS.md`、`README.md`、`docs/IMPLEMENTATION_PLAN.md`；
- `docs/V0.2_DEVELOPMENT_AND_ACCEPTANCE_PLAN.md`；
- `src-tauri/src/sidecar/runner.rs`、`src-tauri/src/sidecar/adapter.rs`；
- `scripts/fetch-ccusage.mjs`、`scripts/fetch-ccusage-antigravity.mjs`；
- `src-tauri/build.rs`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`；
- `src-tauri/binaries/README.md`、`THIRD_PARTY_NOTICES.md`；
- 当前 SQLite 初始化和 Rust/TypeScript `UsageSummary` 定义。

v0.2 的数据路径是：

```text
ccusage.exe 20.0.20
  daily --json --offline --by-agent
                         \
                          -> Rust JSON adapter -> UsageSummary
                         /
ccusage-antigravity.exe
  antigravity daily --json --offline
```

两个子进程由 Rust 顺序监督，单次上限 15 秒；父进程分别排空 stdout/stderr，使用 `taskkill /F /T`
处理超时与退出，并通过 2 秒结果缓存实现 single-flight。Tauri `externalBin` 打包两个 EXE，
`build.rs` 强制检查 staged target-triple 文件，`pnpm fetch:sidecar` 负责下载或构建它们。

SQLite 当前仅创建应用自己的 `usage-cache.sqlite3`，使用 `rusqlite 0.40.2` 的 bundled SQLite；没有业务表。
ccusage `v20.0.20` 及 Antigravity 补丁则使用 `sqlite 0.37.0` 的 bundled/linkage SQLite。若直接把两套源码
一起链接进同一个 EXE，会形成两套 SQLite FFI/amalgamation 的符号、体积和维护风险，必须先统一。

## 4. 目标与非目标

### 4.1 目标

- 从源码构建所有 v0.3 采集逻辑，发布物不含也不查找 `ccusage*.exe`。
- 保留 v0.2 支持的全部正式 ccusage Agent，并加入固定补丁的 Antigravity；统一形成一次 collector 快照。
- worker 崩溃、panic、死锁或异常耗时不拖垮 Tauri UI/托盘进程。
- 对 v0.2 fixture 和脱敏真实数据做逐字段 parity，`UsageSummary` 序列化形状不变。
- 运行时在断网、禁网和无代理环境下得到相同采集结果；不得创建网络 socket 或读取云端凭据。
- 源码、补丁、价格数据、许可证和生成过程均可由仓库内 manifest 审计。

### 4.2 非目标

- 不重做 UI、交互、CSS、窗口、托盘或 `UsageSummary` 字段。
- 不加入路由、设置中心、云同步、账号、遥测、API proxy、通知、月报或通用 Provider 插件框架。
- 不把 ccusage CLI、终端渲染、npm launcher、文档站或命令行兼容性作为产品功能。
- 不把 Antigravity 描述为 ccusage 正式支持；v0.3 明确是固定未合并补丁的 downstream 支持。
- 不在运行时更新定价或访问 LiteLLM/models.dev；v0.3 不做自动更新器。
- 不在本计划步骤修改任何运行时代码。

### 5.2 补丁边界

downstream patch 只允许三类变化：

1. 将 #1487 Antigravity 逻辑移植到 20.0.20 已拆分的 `rust/adapters/*` 架构；
2. 暴露不依赖 CLI 输出的最小内部 collector API；

不得在 vendor 内加入 UI、Tauri、托盘或应用数据库代码。所有偏离上游的行必须能归属到
`PATCHES.md` 中的一个补丁；对 #1487 的语义性改写必须单独说明，不能冒充逐字 cherry-pick。

## 6. 内部 collector API

### 6.1 分层

```text
vendored ccusage adapters
        -> cam collector facade（唯一调用 vendored API 的层）
        -> CollectorResponse v1（worker 私有协议）
        -> 现有 Rust sidecar/collector adapter
        -> UsageSummary（保持 v0.2 公共契约）
```

建议由应用拥有 `collector` 模块/小 crate，vendor 只提供必要的 typed load/report 入口。不要从 CLI 捕获
终端输出，也不要调用 `ccusage ... --json` 的参数解析器。若上游 `ccusage-adapter-all` 只能公开
`run(args)` 并打印输出，downstream patch 应新增返回值 API，而不是在进程内截获 stdout。

### 6.2 协议草案

worker 协议不是 Tauri 公共 API；它仍需显式版本化以便拒绝父/子版本错配：

```rust
struct CollectorRequestV1 {
    schema_version: u32,       // 固定为 1
    since: String,             // 本地日期 YYYY-MM-DD，today - 6
    until: String,             // 本地 today
    timezone: String,          // IANA/系统解析后的明确时区，不依赖子进程猜测
    offline: bool,             // 只接受 true；false 直接拒绝
}

struct CollectorResponseV1 {
    schema_version: u32,
    source_baseline: String,   // v20.0.20+antigravity-c58c1b3
    daily: Vec<CollectorDayV1>,
}
```

`CollectorDayV1`/`CollectorAgentV1` 必须携带现有 adapter 生成 `UsageSummary` 所需的全部信息：日期、开放
字符串 Agent ID、token 总数及 input/output/cache read/cache creation/reasoning、可空成本、真实模型
明细和 missing-pricing 状态。内部 API 不暴露项目路径、session ID、prompt、消息、原始 DB 行或日志内容。

规则：

- worker 只允许一个 request，输出一个 response/error envelope 后退出；stdout 只含 UTF-8 JSON。
- `schema_version`、日期范围、最大响应长度和所有 u64→JS safe integer 边界必须校验。
- unknown Agent ID 继续透传；显示名、稳定排序、七日补零和 `UsageSummary` 组装仍由产品 adapter 负责，
  从而保持公共契约和 UI 不依赖上游类型。
- 一个活跃模型缺价时必须把该 Agent/日期标为价格不完整，产品层输出 `estimatedCostUsd: null`；不得采用
  ccusage CLI 可能显示的“已知部分成本”而误导用户。
- Antigravity thinking token 按 #1487 语义作为 additive reasoning；无法证明类型的差额仍进入
  `unclassifiedTokens`。
- error envelope 只含稳定 code、来源标签和脱敏消息；不得返回原始记录、用户路径或 SQL 内容。

## 7. 自身 EXE worker 隔离方案

### 7.1 启动路径

`main.rs` 在初始化 Tauri/WebView2/托盘/SQLite 前识别一个内部专用参数，例如
`--cam-internal-collector-worker-v1`：

```text
normal launch -> Tauri application
internal flag -> read one stdin request -> collect -> write one JSON envelope -> exit
```

父进程必须通过 `std::env::current_exe()` 获取绝对路径，不搜索 `PATH`，不接收 UI 提供的可执行文件路径。
worker 参数是固定常量；日期和时区通过长度受限的 stdin JSON 传入，避免 shell quoting/injection。

### 7.2 监督与生命周期

将现有 runner 的已验证机制迁移而不是删除：

- `CREATE_NO_WINDOW`、stdin/stdout/stderr 分离、并行排空 pipe；
- 15 秒生产超时（若基准证明不足，变更须有数据和上限）；
- PID 注册、shutdown 二次检查、`taskkill /F /T /PID`、wait/reap；
- single-flight + 2 秒成功/失败结果缓存；
- 应用退出后禁止新 worker，退出/timeout/poll error/panic 后残留进程为 0；
- worker 中的 ccusage 多线程加载仍属于**一个 worker PID**，不得再 spawn ccusage 或 shell；
- worker 检测到内部 flag 已存在时不得递归 spawn 自己。

worker panic 必须被进程边界吸收。父进程把非零退出、无输出、超长输出、malformed JSON、协议版本错误、
超时和进程启动失败映射到现有稳定 `AppError` 边界。stderr 只作脱敏诊断，不显示给 React，也不落盘。

### 7.3 安全与发布约束

- 内部 worker 不是权限边界：它以当前用户权限只读本机 Agent 数据；不得提升权限。
- worker 不初始化 Tauri 单实例、窗口、托盘或应用缓存 DB；这既避免重复 UI，也降低启动时间。
- 安装包、安装目录和运行进程清单中不得出现 `ccusage.exe`、`ccusage-antigravity.exe` 或其他 collector EXE。
- 主 EXE 的 Authenticode 状态同时覆盖 worker 代码；v0.3 仍需按发布策略决定是否签名，不能因只剩一个 EXE
  就宣称已解决 SmartScreen。

## 8. SQLite 统一方案

采用 **`sqlite 0.37.0` bundled/linkage 单一实现**：

1. vendored ccusage `v20.0.20` 和 #1487 都已使用该 crate，保留其只读打开 Agent 数据库的实现；
2. 将应用当前仅用于 `usage-cache.sqlite3` 初始化的 `rusqlite` 代码改写为同一个 `sqlite` crate；
3. 从应用依赖中删除 `rusqlite`，保证最终依赖图只含一个 bundled SQLite C 实现；
4. 应用 DB 仍只执行 WAL/foreign-key 初始化，不借迁移新增业务表；worker 不打开应用 DB；
5. Agent SQLite 一律使用 read-only flags，不执行 migration、PRAGMA 写入或锁定源数据库；应用 DB 才可写。

验收必须用 `cargo tree -d` 和链接产物检查确认没有第二套 `libsqlite3-sys`/SQLite amalgamation；在正在运行的
Antigravity/OpenCode 等 Agent 数据库上验证只读并发，不造成 journal、WAL、锁或源文件时间戳变化。

若 `sqlite 0.37.0` 无法完整替代应用初始化或与 Tauri Windows 链接冲突，实施必须暂停并记录证据；不得用
同时链接 `rusqlite` + `sqlite` 的临时方案跨过发布门禁。可接受的备选是把所有 vendored adapter 统一移植到
`rusqlite`，但这是更大的 downstream patch，需重新评审和基准。

3. 安装包继续包含项目 LICENSE 与 `THIRD_PARTY_NOTICES.md`；新增完整自动生成依赖许可证清单或其资源文件，
   发布前人工审阅 weak-copyleft/notice 要求。
4. 运行 `cargo metadata`、`cargo deny` 或等效 license inventory；任何 unknown/unlicensed、GPL/AGPL 或与静态
   分发不兼容的依赖必须阻断发布，不能只依赖当前 notices 的概括。
5. README/Release Notes 明示 Antigravity 来源为固定未合并补丁、读取本机未公开稳定 schema、成本是估算值。

## 11. 上游升级流程

任何 ccusage、Antigravity 或价格升级都单独提交，流程如下：

1. 查询最新正式 release、tag object/commit/tree、发布说明、许可证和当前 main；不得只看 npm `latest`。
2. 检查该 release 是否已正式包含 Antigravity：命令/adapter、统一报告、文档、测试和 release notes 必须一致。
3. 若已正式包含：以新 release 替换 vendor，删除 #1487 downstream patch，做正式实现与旧补丁的 fixture/真实数据
   对照，防止双计或字段语义回退。
4. 若仍未包含：重新把精确 #1487 后继 commit（或经批准的新 patch）移植到新 release；记录 commit/tree，禁止
   跟踪 PR branch head。
5. 更新 `UPSTREAM.toml`、patch series、Cargo.lock、价格 manifest、THIRD_PARTY_NOTICES 和变更说明。
6. 在干净目录运行 vendor verification、upstream tests、产品 adapter parity、完整自动化、离线构建和 Windows
   安装验收；记录 binary size、采集 median/p95 和 Agent 数变化。
7. 单独人工 review vendor diff；生成代码/价格大文件必须按来源摘要而非肉眼跳过。

升级不得直接在 vendor 中零散编辑后遗忘 patch；不得用 `main`、branch、PR ref 或无 SHA URL作为发布输入。

## 12. 回滚方式

最终 v0.3 不保留可启用的旧 sidecar 运行路径，否则仍会形成隐藏依赖和双实现维护。回滚分两层：

- **发布回滚：** 保留 v0.2.0 tag、安装包和校验值；v0.3 出现采集回归时撤回 v0.3 发布并重新提供已验证的
  v0.2.0 安装包。用户的 Agent 原始数据不由本应用修改，回滚无需数据迁移。
- **开发回滚：** vendor 导入、worker、adapter 切换、sidecar 删除和打包清理分阶段提交；在删除阶段之前可对单个
  提交执行普通 Git revert。不得使用破坏工作区的 reset 作为发布流程。

应用 SQLite 没有新增 schema，因此 v0.2/v0.3 可共享现有空 cache 文件。若实施中发现必须做 schema 变更，应另开
计划并提供 forward/backward migration；不得悄悄纳入本迁移。

## 13. 分阶段实施与验收标准

### Gate 0 — 基线、授权和可构建性冻结

任务：

- 创建 vendor import/verify 工具与 `UPSTREAM.toml`，导入 `v20.0.20` 精确源码、Cargo lock、LICENSE 和价格；
- 保存 #1487 `c58c1b3…` 为来源明确的 patch，完成在 20.0.20 架构上的移植设计；
- 生成完整依赖/license inventory；验证 Rust `1.97.1`（上游固定 toolchain）与当前 Tauri 工具链兼容；
- 先在 Windows x64 编译 vendored collector test target，不接入产品运行路径。

验收：

- commit/tree/价格 SHA 与本文件一致，`vendor:verify` PASS；
- 干净 clone 在源码/价格禁网条件下可以构建（Cargo crates 可由预填 cache 或 `cargo vendor` 提供；不得临时抓取
  ccusage/价格）；
- 上游相关 adapter/core 测试和 Antigravity fixture 测试 PASS；
- 第 15 节中许可证/API/Windows 工具链阻断项均得到明确处置，才可进入 Phase 1。

### Phase 1 — Typed collector facade 与 Antigravity 合并

任务：

- 新增最小 typed collection API，直接调用 vendored adapters，不经过 CLI parser/terminal/stdout；
- 把所有 20.0.20 正式 Agent 和 Antigravity 注册到同一加载快照；
- 实现 `CollectorRequestV1`/`CollectorResponseV1`、缺价标志和 reasoning/unclassified 语义；
- 保持产品 `UsageSummary` 与 React 全部不变。

验收：

- 0/1/2/6 Agent、未知 ID、重复日期/Agent、缺口、乱序、大整数、模型明细、成本有值/零/缺失均有 fixture；
- Claude/Codex/其他 v0.2 Agent 与 20.0.20 sidecar golden JSON 逐字段 parity；
- Antigravity 与 `c58c1b3…` focused golden JSON 在 token/model/reasoning/去重上 parity；
- 同一 Antigravity 数据不会由 unified 与 patch 重复计数；
- React、CSS、Tauri command 和公共 contract diff 为零。

### Phase 2 — SQLite 单一实现

任务：按第 8 节迁移应用 DB 初始化，删除 `rusqlite`，确认所有 Agent DB 只读。

验收：

- 应用 cache 文件名、目录、WAL/foreign-key 行为和非 ASCII 路径测试不变；
- `cargo tree -d`/链接检查只有一套 SQLite；
- 对只读源 DB 的成功、锁定、损坏、缺表、并发写入场景均安全失败或跳过，绝不修改源数据；
- Windows 10/11 x64 均能链接和启动。

### Phase 3 — 自身 EXE worker 与监督

任务：实现内部 worker 入口，把当前 runner 改为 spawn `current_exe()`，保留监督/缓存/退出机制。

验收：

- 正常启动只出现一个 UI/托盘；采集时额外出现且只出现一个同名 worker PID；
- success、non-zero、panic、malformed/超长 stdout、stderr flood、timeout、poll error、shutdown race 后残留均为 0；
- 20 个并发刷新调用最多一个 worker，2 秒内共享同一成功或失败结果；
- worker 不初始化 WebView2/托盘/应用 DB，不递归，不弹控制台窗口；
- 父/子协议版本不匹配稳定失败，消息不泄露用户路径或原始记录。

### Phase 4 — 产品 adapter parity 与性能

任务：把 worker response 接到现有 adapter，运行 v0.2 sidecar 与 v0.3 collector 的 shadow 对照；对照工具仅用于
开发测试，不进入发布包。

验收：

- 相同脱敏 fixture 和获准的本机真实数据上，今天/七日总量、Agent、token breakdown、模型、成本可用性、
  cache share 完全一致；允许的价格数值差异必须逐模型解释并经批准；
- `UsageSummary` JSON schema snapshot 与 v0.2 完全一致，前端所有测试/e2e 无修改通过；
- 至少 10 次 warm run：记录 median/p95、CPU、峰值内存、读取文件数；median 不超过 v0.2 两 sidecar 合计的
  125%，典型 p95 目标不超过 1 秒；超标需有明确处置，不能用“一个 EXE”豁免；
- 主 EXE/安装包体积增量有记录和上限决策，空闲时除计划刷新外不出现 worker。

### Phase 5 — 删除 sidecar 供应链与打包清理

只有 Phase 1–4 全部 PASS 后才能执行：

- 删除 `scripts/fetch-ccusage*.mjs`、`pnpm fetch:sidecar`、`src-tauri/binaries` 的 EXE staging 约定；
- 删除 runner 的 packed/dev sidecar 路径和两个外部文件名；
- 删除 `build.rs` sidecar existence gate；保留 Tauri 自身必要 build script；
- 从 `tauri.conf.json.bundle.externalBin` 删除两项；更新 README、notices 和供应链文档。

验收：

- clean clone 不运行 fetch 脚本即可 `cargo check/test` 和 `pnpm tauri build`；
- MSI/NSIS 内容搜索无 `ccusage*.exe`，安装目录无同名文件；
- 在 PATH 放置伪造 `ccusage.exe` 不影响结果，删除/改名本机 ccusage 安装不影响应用；
- 禁网安装、启动、刷新、托盘和卸载通过；主 EXE 之外无 collector 可执行文件。

### Phase 6 — v0.3 发布验证

完整运行并记录：

```powershell
pnpm install --frozen-lockfile
pnpm vendor:verify
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
```

另外必须实际完成：

- Windows 10 x64 与 Windows 11 x64 的 MSI、NSIS 安装→启动→刷新→退出→卸载循环；
- 标准和真实非 ASCII Windows 用户路径（v0.2 的 waiver 不自动沿用）；
- 断网/防火墙阻断下采集；无 Node/pnpm/Bun/ccusage 安装的干净机；

## 15. 尚未确认的授权、API 与构建风险

以下项目在本调查步骤中**尚未关闭**，实施者不得把它们写成已验证事实：

### 15.1 授权与来源风险

- #1487 是关闭且未合并的贡献，不代表 ccusage 维护者正式接受、审计或支持。MIT 许可允许使用，但产品必须承担
  downstream 维护与安全审计责任。
- 尚未取得 Google 对 Antigravity 私有 SQLite/protobuf 格式的稳定性说明或官方 SDK/API 授权声明；当前实现基于
  本地文件逆向字段。需在发布前由维护者确认这符合产品的法律/合规风险容忍度。本计划不是法律意见。
- 完整 Rust 依赖闭包的 license/NOTICE 尚未针对新 vendor build 实际生成；当前仅核对 ccusage、LiteLLM、
  models.dev 三个直接来源。Gate 0 必须关闭 unknown license。

### 15.2 API 与数据语义风险

- ccusage 20.0.20 的 `ccusage-adapter-all` 主要公开 CLI `run`，内部 typed rows/loaders 不是稳定 library API；需要
  downstream API patch，后续上游升级可能产生较大冲突。
- #1487 基于 20.0.18 的单体 crate，20.0.20 已拆分为 adapter workspace；补丁无法保证机械 cherry-pick，移植时
  可能改变 loader、pricing、错误或去重语义，必须依赖 golden/真实数据 parity 证明。
- 上游当前 main 仍把 Antigravity 写为 unsupported，且公开说明曾回退覆盖不足实现；数据库表、protobuf field number、
  模型 placeholder/alias 可能随 Antigravity 无通知改变。
- “一个 Agent 失败是否使整个快照失败”、损坏 DB 的跳过策略和多 root 冲突策略尚需与 20.0.20/#1487 实际行为逐项
  定义；不得在 facade 中静默吞错造成少计。
- 20.0.20 的 missing-pricing 信息是否能从 typed API 无损取出尚需原型验证；若只能得到部分成本，必须扩展内部 API，
  不能破坏 v0.2 `null` 语义。

### 15.3 构建与平台风险

- 上游固定 Rust `1.97.1`、edition 2024；与项目当前 Rust/Tauri 依赖、MSVC 和 CI 镜像的组合尚未实际编译。
- `sqlite` 与当前 `rusqlite` 同时链接存在重复 SQLite C 实现/符号风险；第 8 节迁移在原型通过前仍是构建阻断项。
- 将全部 adapter 静态链接进 Tauri 主 EXE 会增加编译时间、主 EXE/安装包体积和 worker working set；尚无测量结果。
- 同一 GUI EXE 的 worker 模式能否在 MSI/NSIS、已签名文件、杀毒软件、受限企业策略和 Windows 10 上稳定无窗口启动，
  尚需真机验证。
- ccusage 上游 build script 默认要求 `CCUSAGE_PRICING_JSON_PATH` 或启用联网 fetch feature；仓库内价格注入与禁网
  clean build 尚未实现和验证。
- worker 内部并行读取所有 adapter 可能让一次采集的文件句柄、CPU 或 I/O 峰值高于 v0.2 两个顺序 sidecar；需基准和
  资源上限，不能只比较进程数量。
- v0.2 的非 ASCII 完整 GUI gate 曾被 waiver；v0.3 改变 EXE 启动和 SQLite 链接后，必须重新实际验证，不能继承 waiver。

## 16. 完成定义

v0.3 迁移只有同时满足以下条件才算完成：

1. 安装包和运行时不含、不下载、不查找、不启动任何 `ccusage*.exe`；
2. vendored source、patch、价格、Cargo lock 和许可证来源全部固定并可验证；
3. collector 只在自身 EXE worker 中运行，所有故障路径无残留进程；
4. v0.2 UI、`UsageSummary`、动态 Agent、离线语义和 Windows 10/11 行为通过实际回归；
5. SQLite 只有一个实现，Agent 数据库保持只读；
6. v0.2 sidecar 与 v0.3 源码 collector 的 fixture/真实数据 parity 有记录；
7. 第 15 节所有阻断风险均已关闭或被明确、可审计、对外披露地接受；
8. 新建 `docs/V0.3_RELEASE_VERIFICATION.md` 记录实际结果，计划文件本身不代替验证。

在这些条件满足前，README 和 release notes 不得宣称“已移除 sidecar 依赖”或“Antigravity 正式支持”。
