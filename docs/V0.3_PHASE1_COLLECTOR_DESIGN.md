# v0.3 Phase 1 — 内部 Collector API 设计与实现记录

日期：2026-08-30 · 对应计划：`docs/V0.3_DEVELOPMENT_AND_ACCEPTANCE_PLAN.md` Phase 1（本阶段为其中
"typed collection API" 部分；Antigravity golden parity、`CollectorRequestV1`/`CollectorResponseV1`
跨进程协议等留待 Phase 1 后续任务 / Phase 2）。

## 职责边界

`src-tauri/src/collector/` 是 CAM 代码与 vendored ccusage 源码之间**唯一**的接触点：

- **入方向**：上层只使用 CAM 自有类型（`Collector` trait、`CollectRequest`/`CollectResult`、
  `UsageRecord`/`ModelBreakdown`、`AgentKind`、`CollectorError`）。公共签名不含
  `ccusage_*` crate 类型、`serde_json::Value`、CLI argv 或 stdout 契约。
- **出方向**：`collector::ccusage::AgentCollector` 调用 vendored seam
  `ccusage_adapter_all::daily_report_json_by_agent`（Gate 0 PoC 入口），并在适配层内把 vendor JSON
  转成统一类型。上层禁止依赖 vendor JSON schema。
- **不改变生产路径**：生产采集仍走 `src-tauri/src/sidecar` 的 ccusage sidecar 可执行文件；
  本 API 目前仅被契约测试调用。Phase 2 才切换调用链。

## 核心类型与字段语义

| 类型 | 语义 |
| --- | --- |
| `AgentKind`（= `CollectorKind`） | 采集目标 agent；`id()` 给出 vendor 统一报告里的 agent id（`claude`/`antigravity`），`label()` 为显示名 |
| `CollectWindow` | 日期粒度窗口，**两端均为闭区间（inclusive）**；`new()` 拒绝倒置区间 |
| `TimeZoneSpec` | IANA 时区名（传给 vendor 做 daily 分桶）；请求默认 `utc()` |
| `DataSource` | Phase 1 仅 `Environment`：按 vendor CLI 同样的进程环境变量（`CLAUDE_CONFIG_DIR`、`ANTIGRAVITY_DATA_DIR`…）解析各 agent 数据根 |
| `CollectRequest` | `agent` + 可选 `window` + `timezone` + `source`；agent 与 collector 不匹配 → `InvalidRequest` |
| `UsageRecord` | **每个 agent 每天一条聚合记录**（vendor 可靠提供的粒度；session 级留作后续扩展）。字段：date、agent、input/output/cache_creation/cache_read/total_tokens（全部 `u64`）、`cost: Option<CostNanoUsd>`、`models_used`（排序去重）、`model_breakdowns`（按模型名排序）、`models_missing_pricing`（排序） |
| `ModelBreakdown` | 每模型明细；`missing_pricing: bool` + `cost: Option<CostNanoUsd>` |
| `CostNanoUsd` | 固定点 **i128 纳米美元**（10⁻⁹ USD）。vendor 的 f64 成本只在适配层边界转换一次（round half-away-from-zero，非有限值→None）；下游只做整数运算。`Some(0)` 表示"有价格且计算结果为零"；`None` 表示"无定价/不可用"——绝不用 0 冒充缺价 |
| `CollectResult` | `agent` + `records`（按日期升序；空数据=成功空结果，不是错误） |

`#[non_exhaustive]` 用于 `UsageRecord`/`ModelBreakdown`/`CollectResult`/`CollectorError`/`DataSource`，
为后续字段演进留出空间。未知模型名以 `ModelName` 原样保留；未知 vendor 字段被适配层忽略
（forward-compatible），不阻塞采集。

## 错误分类（`CollectorError`）

| 变体 | 含义 |
| --- | --- |
| `InvalidRequest` | 请求无效（倒置窗口、agent 不匹配、不支持的 DataSource） |
| `SourceUnavailable` | 数据源根目录不存在或不是合法 agent 数据目录 |
| `CorruptData` | 数据存在但无法解析 |
| `DatabaseQuery` | SQLite 数据源打开/查询失败 |
| `VendorAdapter` | vendored 引擎失败（CLI 参数拒绝、loader 内部错误、输出形状不符） |
| `PricingUnavailable` | 定价数据本身不可用（单模型缺价**不是**错误，见 `cost: None`） |
| `Timeout` / `Cancelled` | 预留给 Phase 2/3 的取消与超时路径（当前同步实现不产生） |
| `Internal` | 不变量破坏等内部错误 |

错误 details 只包含简短原因描述，不含密钥、完整日志或用户文件内容；可能引用数据目录路径
（用户本机自有路径，不外发）。vendor 错误是 opaque `CliError(String)`，适配层按已文档化哨兵
`"No valid … data directories"` → `SourceUnavailable` 映射，其余 → `VendorAdapter`；哨兵字符串由
契约测试 `claude_missing_data_dir_maps_to_source_unavailable` 锁死，上游改措辞时测试会大声失败。

## vendor 适配边界与最小扩展

**vendor 修改（0002 patch 已更新，可重放）**：上游把
`ccusage_core::ModelBreakdown::missing_pricing` 藏在 `#[serde(skip_serializing)]` 后，统一 JSON 中
"无定价模型"与"价格为 $0"都渲染 `cost: 0.0`，无法无损表达产品 null/zero 契约。patch 移除该属性，
model breakdown 序列化新增 `"missingPricing": true|false`（纯增量字段）；随之更新 3 处 vendor 测试
期望（copilot、qwen 内联 JSON 与 core insta 快照），全部记入 `patches/0002-cam-downstream-v20.0.20.patch`
并重算 `MANIFEST.sha256`，`pnpm vendor:verify` 保持通过。

除此之外**未改 vendor**：记录类型转换全部在 `collector::ccusage` 完成；vendor JSON 的
`period`/`agents[]`/`modelsUsed`/`modelBreakdowns`/`totalCost` 形状只在本模块出现。

## 已知限制（Phase 1 事实，Phase 2 前置事项）

当前仍使用 sidecar 作为生产采集路径。切换前必须完成：

1. **per-agent 隔离**：vendor seam 一次扫描全部 agent 的数据根；无关 agent 目录配置错误会让
   单 agent 请求失败（claude 根校验即此行为，见契约测试）。需要 vendor 侧按 agent 单独加载的
   API，或在 worker 中按 agent 拆分调用。
2. **数据根路径参数化**：`DataSource::Environment` 依赖进程环境变量；worker 需要在单次进程内
   安全设置（或 vendor 提供路径参数），避免全局 env 变更。
3. **损坏输入的语义冻结**：坏 JSONL 行被 vendor 跳过、坏 SQLite 文件被跳过（两者已由契约测试
   锁定为"跳过并成功"路径）；Phase 1 的 `CollectorError::CorruptData/DatabaseQuery` 尚无 vendor
   触发路径，parity 阶段需决定是否要把"静默跳过"升级为可上报的部分失败信号（计划 15.2
   "不得静默吞错造成少计"）。
4. **会话级记录**：`UsageRecord` 是日聚合；`CollectorRequestV1/ResponseV1` 与 session 明细在
   Phase 1 后续/Phase 2 引入。
5. **single_thread 语义**：Phase 1 强制 `single_thread: true` 保证结果确定性；性能化（并行加载）
   属 Phase 4 测量后的决策。
