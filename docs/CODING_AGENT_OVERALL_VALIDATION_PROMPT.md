# Coding Agent Monitor 总体检查校验 Prompt

复制以下代码块，发送给负责独立审校的 Coding Agent。建议在 T01–T06 完成后运行一次；如果随后实施候选任务，再针对实际新增范围复验。本 Prompt 不授权发布，也不授权把未分配的候选工作补做出来。

```text
你负责对 D:\DevTools\CodingAgentMonitor 的本轮迭代做独立总体检查。

目标：根据实际代码、运行结果和已分配任务，判断交付是否满足要求，发现跨任务遗漏、冲突和回归。不能只根据实施 Agent 的总结或文档中的 PASS 得出结论。

工作模式：
- 本次授权只读审查、隔离 fixture、测试/构建、必要的本地验证，以及写入审校报告；不修改产品代码，不擅自修复缺陷。
- 不推送、不打 tag、不发布、不上传日志/截图/资产，不自行批准 waiver。
- 不重置或覆盖当前工作树。隔离安装生命周期验证不能替换或卸载用户日常使用的实例。
- 优先使用 fixture。不得为了审查在线额度而读取真实 token、cookie、凭据或调用会消耗额度/创建会话的探针。
- 不把缺少环境直接当作 PASS，也不让某个无法执行的原生场景阻止其他可完成的审查。

一、确定审查基线与范围
1. 阅读当前 AGENTS.md、README.md、docs/IMPLEMENTATION_PLAN.md、适用版本的完整计划、docs/CODING_AGENT_ITERATION_PROMPTS.md，以及相关任务交付记录和 v0.3 最终决策。
2. 记录 HEAD、分支、git status、审查开始时间、操作系统、关键工具/依赖版本。当前已有 dirty changes 时明确覆盖哪些文件，不能把它们全部当作本轮产物。
3. 从用户任务记录和计划中列出实际已分配/已实施的任务。若无法确认范围，先检查所有可识别的已改内容，并将范围不确定作为限制，不自行激活候选任务。
4. 核对实际 diff 和源码，不重做 v0.1–v0.3 历史阶段。AGENTS/README 等已经解决的文档问题不得再次当作未修缺陷。
5. 若存在 .codegraph/，理解或定位代码时先用 CodeGraph；没有则跳过。
6. 对每项任务使用 PASS / FAIL / NOT RUN / NOT APPLICABLE；如有历史或新增 waiver，单独列出批准来源、日期、适用范围，不能混进 PASS。

二、审查架构与数据契约
1. 生产仍是 current_exe() 隔离 worker；无外部 sidecar 回退，Rust 仍负责文件/SQLite/进程/托盘，前端不解析 vendor JSON。
2. Rust 与 TypeScript 契约字段、可选/nullable、单位、日期、时区与错误状态一致。组件不能依赖未声明扩展字段或把 unknown 变成 0。
3. 检查 token 加总、缓存分母、reasoning 的来源语义、未分类余量、JS 安全整数和混合缺价。真实零与未知值必须可区分。
4. 检查结构化 Agent 错误时的全量失败策略。除非有本轮单独批准的新策略，不允许静默部分总量或不同时间快照拼接。
5. 检查来源诊断真实性：不能根据空列表声称未安装，跳过记录不能隐藏为“数据完全正常”。公开诊断不含原始日志、完整路径、凭据或对话。
6. 若实施 T07，特别审查不同日期范围/时区/来源的 flight、缓存键和迟到响应：第一请求共享结果的旧设计不能导致 7/30 天查询串用。

三、审查刷新、日期与恢复
逐项验证并记录：
- 首次加载成功、无数据、首次失败；
- 手动/定时/焦点恢复刷新成功和失败；
- 刷新中保留快照、重试恢复、连续点击 single-flight；
- 状态读取与事件注册竞态、迟到响应覆盖、事件监听卸载；
- 托盘与主界面的成功时间、数据日期和失败状态一致；
- 午夜跨日、睡眠恢复、本地时区变化和时间异常；
- 昨日缓存/旧快照不能继续标为今日，读取缓存不更改成功时间；
- 若 T06 已实施，损坏/旧版/未来时间缓存、读写失败、原子写入、退出中断；
- 刷新失败不覆盖最后成功持久化快照；
- 退出取消采集，应用关闭后无孤儿 worker 或自动拉起。

使用可控时钟、隔离环境和明确输入。不得通过修改系统时间或真实 Agent 日志制造场景。

四、审查 UI 与交互
根据实际实现范围检查：
1. 窗口矩阵：420×560、680×700、宽窗口；明暗主题；中文/英文；0/1/4/17 Agent；长名称、未知 Agent、全零和极大值。
2. 状态矩阵：加载、空、首次错误、正常、刷新中、刷新失败、超时效、成本未知、存在来源诊断。
3. 默认窗口核心摘要与主要趋势是否满足计划；更多 Agent 和放大状态自然滚动，不能以裁切、隐藏滚动条或缩小到不可读掩盖问题。
4. 更新时间/数据日期可见；成本口径清楚；比较今日与昨日时注明时间口径；语言、数字、日期和辅助技术标签一致。
5. 展开点击区域、键盘顺序、focus、Escape、读屏标签、reduced-motion 和适用 WCAG AA 对比度。明色检查不能用暗色结果替代。
6. 筛选作用范围明确，Agent 消失有稳定 fallback。若分组为“其余 Agent”，成员在整个可见范围稳定、总和不变、完整明细仍可查看，不能伪造真实 Agent/模型。
7. 图表零值为零；All 与单 Agent 的尺度语义清楚；点击日期详情不会被刷新或范围切换错配。
8. Windows 125%/150% DPI、多显示器和200%文本缩放需要实际原生/对应缩放机制验证；缩小浏览器 viewport 不能冒充全部这些场景。
9. 自动 axe/E2E 与人工视觉走查分别记录。fixture 图片明确标记测试数据，不输出或提交真实使用截图。

五、审查常驻与性能
1. 若 T05 已实施，检查用户主动开启开机启动、启动到托盘、正常窗口几何恢复、首次关闭提示、托盘打开/刷新/退出。
2. 主实例去重不能拦截内部 worker 模式。第二次启动的窗口激活符合设计。
3. 偏好损坏、显示器移除、工作区/DPI变化时窗口仍可见，启动项关闭和卸载行为有实际证据。
4. 测量冷启动到首个可用视图、采集 p50/p95、可见/隐藏常驻 CPU 与内存。明确统计范围包含哪些 app/worker/WebView2 进程、样本数和环境。
5. 同条件对照本轮基线；不能把历史某次 worker p95 当作本次启动时间或应用总资源。
6. 若实现30天历史，长日志场景与后台托盘刷新分别测量；查看历史不能让平时隐藏状态持续承担全量扫描。
7. 性能预算没有明确数值时报告实测与变化、提出预算缺口，不编造达标阈值。

六、检查实际已实施的候选任务
- T07：日期边界、7/30切换、在途请求、成本未知、按日明细、缓存隔离与长日志资源。
- T08：它是研究任务。核对引用可访问性、日期/版本、官方支持程度、账户与Token/额度区分、GO结论的证据和未验证项；没有生产额度功能不算缺陷。不得为了审查研究擅自访问真实账户。
- T09：当前版本来自构建元数据；“查看发布页”不能冒充已检查最新；用户未主动操作时无新增网络；实际支持范围与安装验证、构建身份/hash一致；无自动下载/执行/发布。
- T10：价格来自可靠采集元数据，已定价小计和未知总额区别明确；导出范围/快照/时区一致，CSV特殊字符及公式注入得到处理，取消/失败不破坏数据，无敏感字段。
未分配、未实施的候选任务标为 NOT APPLICABLE，不据此扩大验收范围。

七、执行适用检查
先核对当前项目脚本，再按实际范围运行：
- git diff --check
- pnpm lint
- pnpm typecheck
- pnpm test
- pnpm test:e2e
- pnpm build
- cargo fmt --manifest-path src-tauri/Cargo.toml --check
- cargo check --manifest-path src-tauri/Cargo.toml
- cargo test --manifest-path src-tauri/Cargo.toml
- pnpm vendor:verify（collector/vendor/build相关改动必需）
- pnpm tauri build（本轮产品集成构建；涉及分发/启动生命周期时必需）

使用项目既定锁文件策略；依赖安装不匹配时先记录并在隔离/安全方式下解决，不能为了测试通过修改声明或删除锁文件。
测试失败需要区分基线问题、新回归与环境问题。测试、构建、installer 各自的 PASS 不能互相替代。
需要真实 Windows GUI/重登/重启/隔离安装但当前无法执行的项目，标 NOT RUN，并写可复现的人工步骤。
若审查过程中工作树继续变化，记录新的基线；仅复验受到新改动影响的结果，不把旧结果冒充当前结果。

八、交付审校报告
创建 docs/V0.4_OVERALL_VALIDATION.md；若已有相同文件，保留历史记录并追加本次日期与基线。本文件是审校记录，不能回写历史 PASS 或代替发布授权。

报告须包含：
1. 明确结论：
   - 通过本次实际范围验收；
   - 发现缺陷，需要修复后复验；
   - 证据不足，尚不能判定通过。
   即使没有代码缺陷，缺少本轮必需的原生门禁时也不能宣称完整验收通过。
2. 本次范围、源码/dirty tree 身份、环境与检查时间。
3. 缺陷按严重性排序，每项给出：
   标题、文件及精确行号、触发条件、复现步骤、实际/期望行为、用户影响、证据、建议的最小修复范围。
   对不确定事项标注推断与验证方法，不能用纯审美偏好阻断交付。
4. 任务与验收矩阵：需求 → 实际实现 → 测试证据 → PASS/FAIL/NOT RUN/NOT APPLICABLE。
5. 实际命令与结果；已知基线问题、未运行项、历史 waiver 与本轮风险分开。
6. 跨任务一致性结论：状态/日期、契约、语言/偏好、缓存/请求范围、分组/导出、离线与发布边界。
7. 给下一位 Coding Agent 的最小修复任务列表及对应复验项；不要在本次审查中自行实施。
8. 最终再次确认用户既有改动未被覆盖、真实数据未写入报告或版本控制、没有发布/推送行为。

不能为了给出“通过”降低验收要求，不能把未来功能未实现当作现有任务缺陷，也不能只复制实施 Agent 的自测结论。
```
