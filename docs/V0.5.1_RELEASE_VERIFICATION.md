### MSI explicit-path failures and lifecycle recovery (2026-09-25)

The v0.5.1 MSI built from `cd3f5313004fc4da6370091b1087dd7908b9c697`
was invoked with `msiexec /i`, `ALLUSERS=2`, `MSIINSTALLPERUSER=1`,
`INSTALLDIR=D:\DevTools\cam-v051-upgrade-test`, `/qn` and `/norestart`.
The installer returned exit 0, but AppSearch/remembered-path behavior overrode
the requested directory. It wrote into `D:\DevTools\test\Coding Agent Monitor`,
which contained four orphan files before the attempt. An HKLM uninstall entry
was observed, while the MSI log explicitly reported `Per-User mode` and
`ProductInfo(... Assignment=0 ...)`, which [Microsoft defines as per-user](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-gpsi/38f50015-e1f6-4e36-b80d-a3f1c730e0b1).
The HKLM entry alone is not evidence of machine-scope installation. The HKCU
remembered-path value remained `D:\DevTools\cam-v051-upgrade-test`.
The explicit path-control assertion **FAILED** regardless of process exit code;
it is an additional test beyond the planned MSI lifecycle criterion.

The installed 0.5.1 worker smoke passed as recorded above. Uninstallation
returned exit 0 and left zero CAM uninstall registrations under either HKLM or
HKCU. The four original files were restored from pre-test backups and verified
byte-for-byte by SHA-256; the restored original EXE hash was
`63114B49633BA16B34D329B0CF287AA220C5096FCD3222C6376F55C1BE0AEA15`.
This recovery is evidence about the test host and a passing exercised MSI
install/uninstall lifecycle, not a passing path-control assertion.
The MSI upgrade was deferred until a separate backup and recovery procedure
could be prepared; its later result is recorded below.

A controlled second attempt first set both the HKCU default install-path value
and `InstallDir` value to the absent dedicated directory
`D:\DevTools\cam-v051-msi-test`, then invoked the same MSI with that
`INSTALLDIR`, `ALLUSERS=2` and `MSIINSTALLPERUSER=1`. `msiexec` again exited 0,
but its log shows `AppSearch` replacing the requested path with
`D:\DevTools\test\Coding Agent Monitor`. The dedicated directory stayed
absent, and the 0.5.1 uninstall entry appeared under HKLM. [Microsoft's
AppSearch documentation](https://learn.microsoft.com/en-us/windows/win32/msi/appsearch-action)
describes how a registry search can set a property. The MSI database's
`RegLocator` table searches HKCU, while an in-process `AppSearch` probe under
the current user returned the expected remembered path; the exact source of
the install service's old path is not established. The second uninstall exited
0, left no 0.5.1 uninstall entry in HKLM or HKCU, and restored both HKCU path
values and the four original files to their pre-test state. This repeat
confirms the additional isolated path-control assertion remains **FAIL**.

The subsequent MSI lifecycle started from the published v0.5.0 MSI whose
SHA-256 matched the v0.5.0 release record. It installed version 0.5.0 into
the same legacy directory, then the v0.5.1 MSI upgraded that directory.
Registration and EXE file version changed to 0.5.1, and the old ProductCode
was removed. The upgraded EXE's internal worker returned `status: ok`, 160
tokens and no stderr for an isolated synthetic Claude record. Uninstall exited
0; both product registrations and CAM process count were zero. The four
pre-existing files were restored byte-for-byte and the HKCU remembered-path
values matched their pre-test state. The dedicated test directory remained
absent. This is a passing upgrade lifecycle with a retained path-isolation
failure, not a clean-path claim.
