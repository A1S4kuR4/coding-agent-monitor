## 1. 17-Agent 真实非空 Shadow（实测）

### 1.1 方法

- **harness**：`src-tauri/tests/shadow17.rs`（dev/test only，不进入 release 包）。
- **fixture**：全部 17 个 Agent 非空。数据取自已审计的 golden fixtures
  （`tests/golden/<case>/input/`，committed 文件不被改动），按 Agent 复制到临时目录并做
  **日期归一化**到 shadow 窗口（2026-01-02/03），SQLite 型 Agent（goose/hermes/kilo/opencode/
  antigravity）由 `tests/common/mod.rs` 的真实 vendored schema builders 在测试时生成。
- **两侧同条件**：同一 fixture 目录、同一日期窗口（since=20251228 / 窗口 2025-12-28..2026-01-03）、
  同一 UTC 时区（sidecar 显式 `--timezone UTC`，worker 请求 `timezone:"UTC"`）、同一环境变量集
  （17 个 Agent 根 + HOME/USERPROFILE/XDG/APPDATA 指向空 scratch 目录，不读取任何真实用户数据）。
- **sidecar 路径**：pinned `ccusage v20.0.20`（`daily --json --offline --by-agent --since …
  --timezone UTC`）+ pinned `ccusage-antigravity v20.0.18-antigravity-c58c1b3`
  （`antigravity daily --json --offline --since … --timezone UTC`），与生产一致的参数形状
  （生产同样为两个 sidecar 顺序执行），再经 `normalize_reports` → sidecar UsageSummary。
- **worker 路径**：release CAM 主 EXE 以 `--cam-internal-collector-worker-v1` 启动，stdin 送入
  batch snapshot 请求（17 个 Agent，逐 Agent `Paths` roots）→ `normalize_snapshot` → worker
  UsageSummary。
- **比较**：逐 Agent、逐日：日期、agent id、displayName、六桶 token、total、模型名、模型明细
  （input/output/cacheRead/cacheCreation/total）、cost（nano-USD 精确比较）、
  missing-pricing（worker 原始记录 `modelsMissingPricing` + 日级 cost-null 语义）、去重探针。
  无浮点 tolerance、无仅总量比较。

## 3. Release-to-Release 30-run Benchmark（实测）

### 3.1 条件

- 同一台 Windows 11 x64 机器，交流电源，均衡电源计划，测试期间无其他相关进程。
- 同一 17-Agent 非空 fixture；同一日期窗口与 UTC 时区；同一 roots。
- **每次运行独立启动新进程**：sidecar 路径每轮顺序启动 2 个进程（unified + antigravity，
  生产形状），worker 路径每轮启动 1 个 release 主 EXE（`--cam-internal-collector-worker-v1`）。
  实际进程启动数 = 路径定义本身（sidecar 60 次 / worker 30 次 / 30 轮）；20 并发 single-flight
  只启动 1 个 worker 的证据见 Phase 4A §8（未改变）。
- 每路径 30 轮，两路径逐轮交错执行；run 1 为 first-run，run 2-30 为 OS cache 已热、
  进程重新启动的 warm runs。
- 指标：wall（spawn→响应+normalize，生产形状）、子进程 user/kernel CPU（`GetProcessTimes`）、
  PeakWorkingSet（`GetProcessMemoryInfo` 采样）、I/O 计数（`GetProcessIoCounters`）、
  stdin/stdout 字节、EXE 大小。
- harness：`tests/shadow17.rs::shadow17_release_benchmark_30_runs`（opt-in
  `CAM_SHADOW17_BENCH=1`）；每轮原始数据以 CSV 行输出（`BENCH17 RUN,<path>,<index>,…`），
  完整日志见 `target/bench17_full.log`（canonical）、`bench17_run2.log`、`bench17_run3.log`。

### 3.4 worker 分段耗时（release EXE，env `CAM_WORKER_SEGMENT_LOG=1`，stderr 输出，不污染 stdout/协议/DB）

一次 instrumented run（非 30 轮之内）：

| 分段 | 累计（µs from main） | 解释 |
| --- | --- | --- |
| main（进程内起点） | 10 | — |
| stdin_read | 71 | 请求读取+EOF |
| request_parse | 235 | JSON 解析+校验+into_domain |
| collect_done_claude | 13,468 | **首个 agent 包含惰性 pricing/registry 初始化** |
| collect_done_antigravity | 57,697 | 其余 16 个 agent 平均 ~2.75 ms/个（load mutex 串行，设计约束） |
| serialize | 57,763 | 响应序列化 66 µs |
| write_done | 57,781 | stdout 写入 18 µs |

- worker 内部总耗时 ≈ 57.8 ms；worker spawn wall median 71.0 ms → **spawn→main ≈ 13 ms**
  （进程创建+EXE 加载+运行时初始化）；父进程管道/调度开销 ≈ 17 ms（88.0 − 71.0）。
- 主要开销 = EXE 冷启动（~13 ms，one-shot 设计固有）+ 17 agent 采集（~57.4 ms，vendored
  引擎语义）；协议序列化/反序列化合计 < 1 ms（< 1%）。

## 4. One-shot 优化审计（有证据的结论）

| 审计项 | 证据 | 结论 |
| --- | --- | --- |
| pricing 是否 17 次重复解析 | `vendor/ccusage/rust/crates/ccusage-core/src/pricing.rs`：`EMBEDDED_MODELS_DEV_PRICING: OnceLock<PricingMap>`（进程级单次解析）+ per-Pricing `find_cache`；分段数据：首 agent 13.5 ms（含初始化），后续 agent ~2.75 ms | **无重复解析**，无可优化项 |
| registry/window/timezone/SharedArgs 重复初始化 | `AgentCollector::new` 为 `const`；`SharedArgs` 为每 agent 的栈上小结构体（`src/collector/ccusage.rs`），测量上不可见 | 无可优化项 |
| vendor JSON 不必要中间转换 | domain↔wire 全链路 < 1 ms（分段：parse 0.24 ms + serialize 0.07 ms + 父端 normalize ~0.2-0.4 ms） | 非杠杆（< 1%） |
| worker 是否加载不需要的 Tauri/UI 路径 | `main.rs:10-12`：worker flag 在任何 Tauri/单实例/托盘/DB 初始化**之前**处理并 `exit` | 已最小化；EXE 镜像加载（~13 ms）是单 EXE 设计的固有成本 |

**结论：无可实施的、有证据支持的一次性优化**。剩余成本由（a）one-shot 进程冷启动
（设计收益：干净进程、崩溃隔离）与（b）vendored 采集引擎语义构成。相对 Gate 已 PASS，
无需为优化而改动（未做任何常驻 worker、并行化、采集语义或生产路径改动）。

## 5. 性能决策（更新）

- **相对性能 Gate：PASS**（实测 0.49–1.23，全部 ≤ 1.25；此前基于 debug 采样的 7.13×
  阻断项结论作废）。
- **体验 Gate：PASS**（worker p95 ≈ 104 ms ≤ 1 s，余量 ~9.6×；2 分钟自动刷新间隔的
  < 0.1%；手动刷新 < 150 ms 用户几乎无感）。
- **常驻 worker：不推荐**（维持 Phase 4A 判断）：收益（~13 ms 启动节省）与复杂度
  （framing/crash 恢复/idle 管理/升级兼容/故障隔离下降）不成比例；one-shot 的崩溃隔离
  与干净状态收益保持。
- **Phase 4B 生产切换仍保持阻塞**，等待产品负责人明确批准；本文件只是实测证据，
  不构成切换授权。
