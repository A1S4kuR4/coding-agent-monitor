# v0.3 Phase 4A — 批量快照、UsageSummary Adapter 与 Sidecar Shadow Parity 验收记录

日期：2026-08-31 · 基线：Phase 3（`506646b`）
对应计划：`docs/V0.3_DEVELOPMENT_AND_ACCEPTANCE_PLAN.md` Phase 4 前半部分。

**生产路径事实**：Tauri command `get_usage_summary` 仍调用 v0.2 sidecar runner；
本阶段建立了 batch worker 通路、UsageSummary adapter 和 shadow 对照，但未执行生产切换。

## 1. 批量快照协议（`collector::snapshot_protocol`）

- `CollectorSnapshotRequestV1`：version(=1)、request_id、agents（显式去重、≤32、每个 agent
  独立 DataSource）、公共日期窗口（两端含）、IANA 时区。
- `CollectorSnapshotResponseV1`：version、request_id、agents[]（registry 顺序、日期升序）。
  每个 agent 独立 outcome：`ok{report{records,diagnostics}}` 或 `error{code,message,agent,vendor}`。
- **重复 agent id**：请求侧规范化（首个 source 胜出）；响应侧出现重复 → `Protocol` 错误。
- **未知 agent / 空 agents / 超上限(32)** → `InvalidRequest`。
- 校验：版本门禁、request_id 长度、agent id、六桶不变量、diagnostic kind、agent 归属。

## 2. Worker 批量执行语义

- Worker 收到含 `agents` 数组的请求 → 逐 agent 串行执行（registry 顺序），复用
  `AgentCollector`（无 CLI/stdout JSON）。
- **Per-agent panic 隔离策略：isolate and continue**——每个 agent 的 collect 在独立
  `catch_unwind` 中运行；panic 记录为该 agent 的 VendorAdapter 错误，其余 agent 继续。
  若 panic 破坏进程状态导致记录本身失败，外层 `catch_unwind` 输出整体 fatal——绝不写半个
  stdout 文档。
- 一个 agent 失败不丢弃其余 agent 的成功结果；整体 timeout/cancel/shutdown 由 supervisor
  kill+wait 整个 worker。
- Worker 不初始化 Tauri/应用 DB/sidecar/第二个 worker。

## 3. Worker 快照 → UsageSummary adapter

`sidecar::adapter::normalize_snapshot(snapshot, today, collected_at) -> Result<UsageSummary>`：

- **partial failure 策略**：结构化 agent error（SourceUnavailable/DatabaseQuery/VendorAdapter/
  Internal）→ 整次刷新失败（v0.2 一致：sidecar 失败=刷新失败，沿用旧缓存）。成功 agent 的
  per-record diagnostics（跳过损坏文件等）保持 v0.2 语义：数据存活、diagnostic 上浮。
- **字段映射**：日期（每日聚合）、agent id（vendor id）、input/output/cacheRead/cacheCreation、
  reasoning（Phase 1 六桶：显式报告的 reasoning/thinking）、unclassified（残差）、total、
  模型明细（input/output/cacheRead/cacheCreation/total）。
- **成本**：worker 的 nano-USD → f64（除以 1e9，一次舍入）；缺价（`cost: None`）→ 该 agent
  `cost_known=false` → 该日 `estimated_cost_usd: null`——不输出已知模型的部分成本。
  `Some(0)` 与缺价 `None` 严格区分。
- **JS safe bound**：`emit_day_total` 拒绝 > 2^53-1 的 agent/day total（与 sidecar 路径一致）。
- **共享聚合管线**：`summarize_days` 抽取自 `normalize_reports`，两条路径（sidecar JSON 解析
  和 worker 快照）在七日窗口、日期缺口补零、排序、六桶 breakdown、cache share 上使用同一代码。
- **display name** 保持 v0.2 的 `display_name()` 映射。
- 模型列表排序去重。

## 4. Shadow Harness（`tests/sidecar_shadow.rs`，dev/test only）

同 fixture + 同 env vars + 同 `--since 20260101` + UTC：
- **sidecar 路径**：运行 pinned `ccusage v20.0.20` exe
  （`daily --json --offline --by-agent --since <window>`）→ `normalize_reports` → sidecar UsageSummary。
- **worker 路径**：supervisor 启动产品 EXE（batch snapshot 请求，Paths 与 sidecar env 相同的
  fixture roots）→ `normalize_snapshot` → worker UsageSummary。
- 逐字段比较：日期、agent id/display name、六桶 tokens、total、模型名和明细、成本
  （nano-USD 对比）、agent 数量。无浮点 tolerance、无仅总量比较。
- 不上传数据、不联网（sidecar `--offline`）、不写 Agent 源数据、不输出原始日志/session/
  prompt/SQL/完整用户路径。
- **不进入 release 包**：`tests/sidecar_shadow.rs` 是集成测试二进制，Tauri 打包只包含主 EXE
  和 sidecar；shadow harness 从未被打包。

## 7. 性能基线（10 warm runs，同 fixture/窗口/时区/机器）

| 指标 | sidecar v20.0.20 | worker (batch snapshot) |
| --- | --- | --- |
| median | 28.1 ms | 200.4 ms |
| p95 | 44.0 ms | 212.7 ms |
| worker/sidecar ratio | — | **7.13×** |

**Phase 4B 阻断项**：worker median 超过 sidecar median 的 125%（200ms / 28ms = 7.13×）。
来源分析：worker 每次冷启动产品 EXE + 进程内 vendored workspace 编译产物加载 + SQLite
打开/关闭 + JSON 序列化/反序列化；sidecar 是常驻磁盘的 Node.js 快照（无进程创建成本，
OS page cache 热切）。Phase 4B 切换前需评估：常驻 worker 进程复用、或接受该开销
（每 2 分钟刷新一次时 200ms 仍远低于刷新间隔）。

## 8. single-flight 生产形态验证

- `worker_runner::collect_snapshot`：20 个并发完整刷新调用共享恰好 **1 个 worker 进程**
  （spawn-marker 计数 = 1，非仅 future 数量断言）。
- 成功/失败缓存 2s（与 sidecar runner 相同）；timeout/cancel 后下一次刷新恢复。
- 任意时刻最多一个 collector worker PID；完成后 PID 和句柄消失（supervisor kill+wait 保证）。

## 9. 生产仍使用 sidecar

- `commands/usage.rs` 的 `get_usage_summary` 未修改：仍调用 `sidecar::collect_usage()`。
- sidecar 二进制和 fetch/staging 脚本未删除。
- shadow harness 不在 release 包中（集成测试二进制不参与 Tauri 打包）。

## 10. Phase 4B 切换条件（尚未完成）

1. **性能阻断项**：worker median 超过 sidecar 的 125%（当前 7.13×）——需要评估常驻 worker
   或确认开销可接受；
2. npm sidecar 与 vendored engine 的已知差异审批（差异清单 #1 已文档化并批准）；
3. 安装包文件清单变更（worker 不需要额外文件——同一个 EXE）；
4. 生产切换 commit（`get_usage_summary` 调用 `worker_runner::collect_snapshot` +
   `normalize_snapshot`）；
5. 联网 vendor 重建复验（发布 Gate）。
