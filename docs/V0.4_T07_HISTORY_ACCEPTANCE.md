## 实现与口径

- 新增 Rust/TS `HistoryUsage`：`scope`、`collectedAt`、`days`、可空的
  `estimatedCostUsd`、`coverage`。`UsageSummary.last7Days` 与 T06 持久格式不变。
- `get_usage_history` 仅接受 7/30；Rust 捕获本地日历日和 IANA 时区，两端包含，
  向前 6/29 日。`spawn_blocking` 执行同 EXE worker；React 不读源文件。
  默认 7 日复用统一今日状态；30 日仅点击范围或用户手动刷新时查询。
  周期、焦点、启动、托盘刷新不发起 30 日工作；已发起的历史工作仍可在隐藏后完成。
- `normalize_history` 复用现有日聚合、不变量和诊断脱敏；缺日零桶表示成功查询未找到
  记录，不代表未安装。任一结构化来源错误/整批 fatal 仍整体失败；跳过诊断无法定位
  日时标记整个范围可能不完整，选日详情再次显示该风险。
- 全范围成本忽略无用量日；任一有用量日缺完整成本时总额 `null`，不输出部分小计；
  全零范围不适用。数值零仍为真实已知零。单日缺价原因沿用 T02。
- 生产 batch flight 在 T01 已按日期/时区/来源/协议区分。本次保持一个 worker 槽，
  改为迭代等待，原子检查缓存并占槽，清槽后再通知等待者；短缓存最多两个身份，
  成功/失败均保留 2 秒，过期惰性移除。身份不同不清除仍有效的另一范围缓存。
  缓存同时保留真实完成时间，读取不重写。输入协议先验证再进入 flight/cache。
  source 是生产固定 Environment 或测试显式 roots，测试 request id 不影响等价查询。
- 历史响应不进入 CollectionCoordinator，不发托盘状态事件，不写 T06 恢复文件。
  未新增 SQLite 表、会话索引、文件监听、常驻 worker、依赖或默认网络请求。
- UI 范围切换递增请求序号，立即清空旧范围/选日/浮层；失败显示错误和重试，不显示零。
  旧响应或卸载后的响应不更新视图。30 日快照显示范围、时区、原成功时间和过期提示；
  自动刷新今日不会替换其历史范围。选择仅在当前日期集合内有效，回到今日清除选日。
- 30 日每柱保留日期、绝对数值和可聚焦按钮，图表自身横向滚动，页面正常纵向流动；
  不把 30 组标签挤进七日宽度。T04 全部/单 Agent、稳定分组与缩放规则按可见范围重算。
  选日固定面板显示日级构成、全部 Agent 与已有模型构成；筛选趋势与全部明细分别标注。
  全范围 Token 加总使用 BigInt，避免多个 JS-safe 日总量相加失精度。

## vendored 能力与扫描成本

源码证据：`collector/ccusage.rs::vendor_shared_args` 已设置 `since/until/timezone`，
保持 `offline: true`。vendor `ccusage-adapter-all/src/loader.rs` 的
`load_claude_rows` 在 `load_daily_summaries` 后按日期过滤；`load_codex_rows`
在 `load_codex_events` 后过滤；通用 loader 也有先 load entries 再过滤的路径。
Claude `adapters/claude/src/daily.rs::read_daily_usage_file` 读取文件内容并逐行解析。
因此本次增加的是有边界的查询与正确结果身份，不声称扫描从全历史降为 7/30 日。

实施前在计划 §11.8 设定本次合成场景预算：100,000 条长日志，30 日 worker p95 ≤10s、
峰值 working set ≤512 MiB；UI 操作反馈 ≤100ms。此预算不是旧发布 Gate，也不扩大平台支持。

实际命令：`python -X utf8 scripts/history-benchmark.py --runs 30`。
产品 release EXE 由本次 `pnpm tauri build --no-bundle` 构建。只调用内部 worker 标志，
从未启动 GUI；一个显式临时 Claude root，100,000 条唯一合成记录分布于 60 个本地日，
25,977,780 bytes。按 7/30 与 30/7 交替各 30 次，新进程每次重算、OS 文件缓存不清除。
脚本断言实际有 7/30 个日聚合且无诊断，不读取或打印真实日志；临时文件自动清理。

| 范围 | p50 墙钟 | p95 墙钟 | CPU 时间 p50 | worker 峰值 working set |
| --- | --- | --- | --- | --- |
| 7 日 | 241.94 ms | 263.95 ms | 226.56 ms | 74.85 MiB |
| 30 日 | 246.75 ms | 266.94 ms | 234.38 ms | 74.86 MiB |

墙钟包含进程创建、协议请求/响应和退出。CPU 为 Windows GetProcessTimes 的 kernel+user，
内存为每 5ms 读取 GetProcessMemoryInfo.PeakWorkingSetSize；不包含主程序/WebView2，
不代表系统总内存或提交量。该样本符合预算，无实测依据要求建设增量缓存。

UI：独立 Playwright 模拟延迟 IPC 场景，真实 React 点击到下一帧加载反馈 **19.4ms**；
回到 7 日后迟到 30 日结果不覆盖。包含 Playwright 自动化开销的切换到完整图表时间
166.8ms（16 worker 测试负载）/51.5ms（单 worker 聚焦复测），不能把自动化往返时间
当作纯 UI 处理时间。此 UI 证据是浏览器层，**不是原生 WebView2 与长日志端到端实测**。

无效试跑单列：初版 synthetic JSON 带空格，触发 vendor 的精确 usage 标记预筛选，
返回零行；其 30 次结果全部作废。随后尝试 17 个空显式 roots 时 Hermes/Goose/Copilot
给出来源诊断或来源错误，亦作废；改用与聚焦长日志场景一致的单 Claude root 并增加
行数/诊断断言后才计入上表。没有通过删除断言把空源当作成功性能。
